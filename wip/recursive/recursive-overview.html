PR overview · mthds-plugins

Building .mthds methods top-down, valid at every step

This PR rewrites the mthds-vibe skill from a single-pass generator into a stepwise-refinement builder: capture the whole job as one pipe signature, then refine it layer by layer into a runnable method that validates at every intermediate save.

TL;DR

  • New primitive: PipeSignature — a contract-only forward declaration (a C-style header) for a pipe: its inputs, output, and intended type, with no implementation yet.
  • New methodology: top-down layered refinement. Start with the whole job as one signature; each step adds one file that implements one signature — as an operator (leaf) or a controller that forward-declares its own children. The backlog is the library's own pending_signatures list, drained breadth-first until empty.
  • The artifact is always valid. We validate leniently (--allow-signatures) after each layer — unimplemented signatures mint a mock of their output — then strictly once at the end. We made both validation hooks (Claude + Codex) lenient so in-progress saves aren't blocked, with a non-blocking nudge listing what's left.
  • It works. Dogfooded end-to-end on a real 3-layer method (incident_report): every intermediate save passed the lenient hook, the final strict gate held, and the finished method ran (dry-run).
  • One hard limitation we hit: concepts cannot be lazily structured across files. A concept's shape must be fixed in the file that introduces it. We document the workaround (structure-at-introduction + hoisting) — see § The concept wall.
  • Status: all code/skill/doc changes landed and green; the only thing left is the release, gated on the unreleased pipelex runtime support (Part A+B).

Why — from one shot to refinement

The old mthds-vibe tried to emit a whole method in a single pass. For anything multi-step that means holding the entire pipe graph and all its concepts in one go — and the in-progress file is invalid until the very last line, so the validation hook fights you the whole way down.

The fix mirrors how engineers actually decompose: commit to a contract first, implement later. Write the signature of the top pipe, then refine one signature at a time, one level down, leaving the not-yet-built parts as further signatures. Every intermediate state is a complete, valid, resumable library — the half-built method is its own todo list.

The primitive — PipeSignature

A PipeSignature declares a pipe by its contract only: description, inputs, output, and an optional signature_for hint. No prompt, no steps — just the promise of what the pipe takes and returns.

The header (a forward declaration)

[pipe.build_incident_report]
type          = "PipeSignature"
description   = "Notes → structured report"
inputs        = { notes = "Document" }
output        = "IncidentReport"
signature_for = "PipeSequence"  # hint only

The concrete (added later, reconciles)

[pipe.build_incident_report]
type   = "PipeSequence"
inputs = { notes = "Document" }      # same…
output = "IncidentReport"           # …contract
steps  = [
  { pipe = "extract_notes", result = "pages" },
  # …
]
ℹ︎ signature_for is a hint, not a binding
It records the intended next-level type so the expander knows whether to write an operator or a controller. It may be overridden, it may not be "PipeSignature", and it can be omitted. The decision rule: a single cognitive/IO step → operator; multiple steps, iteration, branching, or parallelism → controller.

The methodology — refine layer by layer

One signature in, its implementation out. If it's an operator, the branch is done. If it's a controller, it wires sub-pipes and forward-declares each not-yet-built child as a new signature — those new headers join the backlog. Repeat until the backlog is empty.

Step 2 is the whole engine: pop → add one file → re-validate → recompute the backlog. Controllers grow the backlog; operators shrink it. Draining the full current set each round walks the tree breadth-first by construction.

Autonomy

The loop is automatic. The only optional interaction is at Step 1 (announce the captured top-level contract so the user can interject). After that, the leniently-valid checkpoints and the regenerated dry_run.html are the review surface; the user can interrupt at any time.

Always-valid — lenient vs strict

The invariant that makes this safe: every unbuilt pipe is a reachable signature, so the assembled library passes lenient validation at every step.

ModeFlagReachable signature…Used
Lenient --allow-signatures …is accepted; mints a mock of its declared output on dry-run after every layer, and by the save hooks
Strict (default) …is rejected — passing means no placeholders remain once, at finalize (Step 3) + always by run
✓ On a signature-free bundle, lenient ≡ strict
So flipping the hooks to lenient is a no-op for mthds-build, hand-edits, and finished methods. It only unblocks in-progress recursive saves. The strict gate didn't disappear — it moved to the explicit finalize step and to run, which always reject signatures. An unfinished method can never be run by accident.

A successful validate reports pending_signatures — the library-wide list of pipes still typed PipeSignature. That list is the backlog. It's never hand-tracked or reconstructed as a tree; it's recomputed from the library each layer.

The additive multi-file model

The artifact is a library, not one file: a directory of same-domain .mthds files loaded together with -L. Construction is purely additive — each refinement adds a new <code>.mthds file; no existing file is ever rewritten, and there is no merge step.

At load, a concrete pipe satisfies a signature of the same code — the definition wins. So the same code legitimately appears as a header in one file and as a concrete in another. The two reconcile by concept identity, not byte-string: bare ↔ qualified (Brief ≡ domain.Brief), native equivalents (Text ≡ native.Text), multiplicity compared structurally.

The same pipe code as a header in one file and a concrete in another — they reconcile at load. This is what lets refinement be append-only.

Two failure modes we deliberately triggered (and recovered from)

Both were caught by the live save hook, which blocked the write and handed back an agent-actionable reason. Each error is real output from the dogfood.

Contract mismatch — definition diverges from its frozen header

We wrote assemble_report with output = "Timeline" while its header says IncidentReport:

# Error: ValidateBundleError
Pipe 'incident_report.assemble_report' is declared with mismatched contracts:
  assemble_report.mthds       … output='Timeline'
  build_incident_report.mthds … output='IncidentReport'
A forward declaration (PipeSignature) and the matching declaration
must agree on inputs and output.

Recovery rule: conform the definition to the frozen header — never edit the header (the parent depends on that contract). We rewrote assemble_report as the correct PipeCompose construct → IncidentReport.

Concept collision — two controllers want the same concept name (D5)

Both sub-sequences naturally wanted a RawFindings concept. Reusing the code triggers the loud backstop:

# Error: ValidateBundleError
Concept 'incident_report.RawFindings' is declared in two different
bundle files: analyze_timeline.mthds and assess_remediation.mthds.
Please remove one of the declarations or rename one of the concepts.

Prevention rule (D5): before introducing an intermediate concept, check it isn't already declared, and derive a unique code namespaced from the parent (RawFindings → RemediationFinding). Serial execution makes this nearly free; the duplicate-declaration error stays the backstop. (Parallel-sibling collisions are a separate, deferred concern — they return with fan-out.)

The one non-obvious bit: two output streams

To read pending_signatures as JSON and keep the error classifier working, the Claude hook pins both stream controls. --format governs the success envelope on stdout; --error-format governs the error report on stderr — and --error-format inherits --format when omitted. So --format json alone would JSON-ify errors and break the markdown classifier.

# Stage 3 — blocked every in-progress save
mthds-agent validate bundle "$FILE" -L "$DIR/"
# Stage 3 — lenient; one invocation, both streams pinned
mthds-agent validate bundle "$FILE" -L "$DIR/" \
  --allow-signatures --format json --error-format markdown

# success → read pending_signatures from JSON stdout → non-blocking nudge
# failure → errors stay markdown on stderr → classifier UNCHANGED (blocks input-domain)
ℹ︎ Scope note (decision D1)
v1 runs the layer loop inline/serial on both targets. The parallel fan-out (a per-signature worker sub-agent + a new agents/ plugin component) is deferred to a follow-up. Correctness is identical; only per-signature parallelism and context isolation are dropped.

The concept wall — what doesn't work

Signatures give pipes a clean header/definition split. Concepts have no such split. The additive model imposes three hard rules on concepts, and together they forbid the "lazy structuring" we originally wrote into the skill. We proved each with a throwaway probe — all fail with error_domain: input, even under --allow-signatures.

✗ Rule 1 — must be declared
A referenced-but-undeclared concept is a hard error. Every concept a pipe names must be declared somewhere in the assembled library at every layer.
✗ Rule 2 — declared exactly once
The same concept in two files is a hard error (declared in two different bundle files). You cannot split a declaration, nor add structure to it from a second file.
✗ Rule 3 — a field-read needs the field to exist
Reading x.field on a simple concept fails at dry-run (Cannot resolve path 'x.field': attribute 'field' not found) — lenient validation does not mock-tolerate it.
The three probes (real output) 
# Rule 1 — concept referenced, declared nowhere
'Widget' in pipe.make_widget.output is not declared in domain 'probe'

# Rule 2 — same concept declared in two files
Concept 'probe.Widget' is declared in two different bundle files:
  'bundle.mthds' and 'refine_widget.mthds'. … rename one of the concepts.

# Rule 3 — field-read on a simple concept (even under --allow-signatures)
Dry run failed … Cannot resolve path 'widget.label':
  attribute 'label' not found

Put together with "never edit an existing file": a concept's shape must be fixed in the single file that introduces it. You cannot introduce a concept simple and add fields later — by the time a consumer field-reads it, the introducing file is already written and frozen, and a second declaration is illegal. So "introduce simple, structure when a consumer reads a field" — the wording we originally shipped — is not achievable across files.

The workaround we adopted: structure-at-introduction + hoisting

Decide a concept's shape from the consumers the introducing controller wires. If any consumer field-reads it, declare it structured now. If it's only ever consumed whole (@x in a prompt, or mapped wholesale), keep it simple. When a sibling field-reads a concept, hoist it to the common parent that wires both producer and consumer, and structure it there.

In the dogfood this is exactly why IncidentSummary/Timeline/Remediation were structured up in build_incident_report.mthds (the parent that wires both producers and the assemble_report consumer), while RawFindings stayed simple (consumed whole).

⚠︎ The genuine gap (logged as a future pipelex feature)
True cross-layer lazy structuring would need additive concept refinement — letting a later file add structure to a concept declared simple elsewhere. That's a pipelex runtime change, out of v1 scope. Until then, structure-at-introduction is the discipline, and the dogfood confirms it works in practice.
